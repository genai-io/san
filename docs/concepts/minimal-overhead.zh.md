# Minimal overhead：San 把开销省在哪里？

一个 Agent 从启动到回答，要付三笔开销：运行客户端、给模型准备上下文，以及重复处理前几轮已经看过的内容。San 分别做了三件事：**客户端做轻，默认提示词做短，多轮对话尽量复用缓存。**

## 1. 一个二进制，不另外装运行时

San 用 Go 编译成单个可执行文件，不需要另外装 Node.js 或 Python。对经常从终端、CI 或临时环境启动 Agent 的人来说，这意味着更少的安装步骤，也不必每次多启动一套语言运行时。

在一组 Apple Silicon 上的对照测试中：

| 指标 | San | Claude Code |
|---|---:|---:|
| 下载大小 | 12 MB | 63 MB |
| 磁盘占用（含所需运行时） | 38 MB | 约 175 MB |
| 启动内存（峰值 RSS） | 约 32 MB | 约 189 MB |

这些是[特定版本的实测值](../operations/benchmark.md)，不是所有平台的固定值。

## 2. 系统提示词只交代模型不知道的事

我们很早就开始删掉大段通用系统提示词。模型能力增强以后，很多编程常识和通用工作方法不必每轮重讲。San 只保留这个运行环境特有的信息：代理的角色、必要的行为规则，以及它怎样和运行时交互。谁有权调用工具，则由程序检查，而不是靠提示词约束。

在一组[单独的空项目首轮测量](../operations/benchmark.md#7-context-overhead-first-turn)中，San 的默认系统提示词约 **262 tokens**；加上默认工具定义，固定输入约 **2.3k tokens**。Claude Code 在对应测试中约为 **20.9k tokens**。两边计数方式不同，适合看量级，不适合算精确倍数。衡量的是用户还没开始工作时，框架本身已经占了多少上下文。

## 3. 不重写旧前缀，让下一轮用上缓存

提示词缓存靠请求前缀匹配。如果每轮都改开头的系统提示词，后面的对话即使没变，也可能无法命中缓存。San 尽量保持系统提示词、工具定义和已有消息稳定。项目指令或技能目录有变化时，将更新附在新的用户消息上；技能正文只在调用时加载。

```text
上一轮  [固定指令和工具定义] [已有对话]
下一轮  [固定指令和工具定义] [已有对话] [新消息和提醒]
         <------- 已有前缀：可命中缓存 ------->
```

命中时，供应商可以复用已有前缀的预填充（prefill），而不必重新计算整段历史。`/btw` 等旁路提问也尽量复用主对话前缀，但不会把问题和回答写回主对话。看用量时，`cache_read` 反映有多少输入 tokens 来自缓存；实际占比会随模型、供应商和会话变化。

**精简提示词省的是上下文窗口；缓存省的是重复计算，并可能降低输入费用。** 命中的 tokens 仍然占窗口。详见[上下文分层与缓存设计](harness-channels.md)。

## 4. 快的是从发起到拿到结果

在同一台 Apple Silicon 机器、使用同一个 Claude Sonnet 4.6 模型的测试里，San 的版本命令约 **0.01 秒**完成；简单的一次性问答平均约 **2.4 秒**，需要读文件的任务平均约 **3.0 秒**。后两项是从启动到任务完成的端到端耗时，不是首 token 延迟。实际响应还取决于模型、网络、任务和缓存状态。[完整数据与方法](../operations/benchmark.md)

**Minimal overhead 不是让模型少做必要的工作，而是让客户端少占资源，让模型少处理重复的输入，把空间和时间留给当前任务。**
